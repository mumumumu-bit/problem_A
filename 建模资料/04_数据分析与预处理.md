# 数据分析与预处理 —— 《通用神经网络处理器下的多核调度问题》

---

## 一、数据理解

### 【数据概况】

**数据来源**：赛题提供的 100 个神经网络计算图 JSON 文件（`case_001.json` ~ `case_100.json`），位于 `data/` 目录下。所有计算图均基于真实深度学习模型（如 ResNet、VGG、Transformer 等）的分块计算数据流生成，体现了实际 NPU 编译器面对的图结构多样性。

**数据规模**（基于抽样 24 个算例的批量统计）：

| 统计量 | 最小值 | 最大值 | 中位数 |
|--------|:------:|:------:|:------:|
| 操作节点数 (ops) | ~796 | ~23,997 | ~1,700 |
| 张量节点数 (tensors) | ~889 | ~26,666 | ~1,850 |
| 有向边数 (edges) | ~1,899 | ~63,990 | ~4,300 |

**规模分布特点**：
- 算例规模**非单调递增**，编号与规模无直接对应关系。例如 case_025（23,997 ops）远大于 case_100（1,654 ops），而 case_001（1,001 ops）已超过 case_100。
- 大致可分为三类：**小型（< 2,000 ops）**约 40 个、**中型（2,000~10,000 ops）**约 45 个、**大型（> 10,000 ops）**约 15 个（含 case_025、030、085 等超大算例）。

**数据结构**：每个 JSON 文件含三个顶层数组：
- `tensors`：张量节点列表，含 `id`、`pos`（DDR/L1/UB）、`size`（字节）
- `ops`：操作节点列表，含 `id`、`op`（类型）、`pipe`（流水线）、`cycles`（执行周期）
- `edges`：有向边列表，含 `source`、`target`，形式为 op→tensor 或 tensor→op

**统计比例**：ops : tensors : edges ≈ 1 : 1.1 : 2.7（在所有算例中基本稳定）

**数据在赛题中的作用**：
- 计算图是建模的唯一输入对象——一切切图、调度、优化决策都基于对图结构的分析
- 不同规模、不同结构的计算图考验算法的**通用性和可扩展性**
- 算例规模覆盖广（相差约 30 倍），要求算法在小图和大图上均能高效运行

### 【变量说明】

#### 输入变量（来自计算图 JSON）

| 字段 | 类型 | 含义 | 建模作用 |
|------|------|------|----------|
| `tensors[].id` | int | 张量唯一标识 | 参与数据依赖关系构建 |
| `tensors[].pos` | string (DDR/L1/UB) | 张量存储位置 | 决定存储约束类别（L1/UB有容量限制） |
| `tensors[].size` | int | 张量字节数 | 核内容量占用计算、搬运量计算 |
| `ops[].id` | int | 操作唯一标识 | 切图决策的基本单元 |
| `ops[].op` | string | 操作类型（COPY_IN/COPY_OUT/MATMUL/ADD/RELU...） | 计算量估算、Pipe归属推断 |
| `ops[].pipe` | string (PIPE_M/PIPE_V/PIPE_MTE2/PIPE_MTE3) | 占用流水线 | 流水线负载均衡分析 |
| `ops[].cycles` | int | 执行周期数（核内计算op使用） | 计算负载估计、关键路径分析 |
| `edges[].source` | int | 边起点 id | 拓扑依赖关系 |
| `edges[].target` | int | 边终点 id | 拓扑依赖关系 |

#### 固定配置参数（来自 config.txt）

| 参数 | 取值 | 作用 |
|------|------|------|
| L1 容量 | 524,288 bytes | 每核 L1 片上容量硬约束 |
| UB 容量 | 131,072 bytes | 每核 UB 片上容量硬约束 |
| DDR 带宽 | 60 bytes/cycle | 共享带宽竞争模型的关键参数 |
| task_cross_core_wait | 1,000 cycles (问题1) | Task 切换代价 |
| task_same_core_wait | 100 cycles (问题1) | 同核 Task 切换代价 |
| cross_core_copy_delay | 500 cycles (问题2/3) | 跨核 COPY 同步延迟 |
| cache_capacity | 1,048,576 bytes (问题3) | L2 Cache 容量 |
| cache_bandwidth | 250 bytes/cycle (问题3) | Cache 命中带宽 |

#### 输出变量（评估器给出）

| 指标 | 含义 | 优化方向 |
|------|------|----------|
| Makespan | 全局完工时间（cycles） | **最小化** |
| added_copy_bytes | 新增 DDR 搬运量 | 尽量小 |
| cache_hit_rate | Cache 命中率（仅问题3） | 尽量高 |

#### 关键影响因素

| 因素 | 对模型结果的影响 |
|------|-----------------|
| 子图数量与大小分布 | 影响并行度上限、跨子图通信量和单核存储压力 |
| 子图边界处的张量生命周期 | 决定是否需要 DDR 中转（问题1）或片上驻留（问题2） |
| 单核合并后的总 L1/UB tensor 量 | 决定溢出频率——这是问题 2/3 的核心瓶颈 |
| 各核负载均衡程度 | 影响关键路径长度和整体 Makespan |
| 共享输入数据的切分位置 | 影响数据重复读取代价（多个子图各自 COPY_IN） |

## 二、数据质量分析

### 【数据质量分析】

**1. 缺失情况**：抽样检查 24 个算例，所有 JSON 均包含完整的 `tensors`、`ops`、`edges` 三个数组，每个数组内字段完整。**无缺失值**。

**2. 异常数据**：
- 所有 `id` 为整数且无重复（单个 JSON 内）。op id（1~N）与 tensor id（≥10001 或 ≥1，不同算例不同）空间不重叠，符合赛题规范。
- `cycles` 值均为正整数，最大约 4,120 cycles，无异常极端值。
- `size` 值均为正整数，最大约 18,432 bytes（即 ~18KB 的单个 tensor），远小于 L1/UB 容量（单个操作输入+输出不超过对应缓存容量，赛题保证）。
- **无异常数据**。

**3. 重复数据**：每个 JSON 内无重复 id，边集合中无重复 `(source, target)` 对。**无重复**。

**4. 数据一致性**：
- 所有 edge 的 `source` 和 `target` 指向的 id 均在 ops 或 tensors 中存在的有效节点。
- tensor 的 `pos` 字段仅在 `{DDR, L1, UB}` 三种取值中。
- op 的 `pipe` 字段仅在 `{PIPE_MTE2, PIPE_MTE3, PIPE_M, PIPE_V}` 中。
- COPY_IN/COPY_OUT 操作仅连接 DDR↔片上（L1/UB）的张量。
- **数据高度一致**。

**5. id 空间特征**：
- case_001~case_008 左右：tensor id 从 10,000,000 起跳，op id 从 1 起跳，差距极大
- 后续算例（case_010 起）：id 从 1 开始紧凑编号，op 和 tensor 共享 id 空间但值域不重叠
- 这不影响建模（算法内部统一转换为 `o{id}`/`t{id}` 命名空间），但需注意 id 空间差异

---

### 【数据处理方案】

**结论：赛题数据质量极高，无需进行传统意义上的数据清洗。**

| 问题类型 | 状态 | 处理方案 |
|----------|------|----------|
| 缺失值 | 无 | 不需要处理 |
| 异常值 | 无 | 不需要处理 |
| 重复数据 | 无 | 不需要处理 |
| 不一致 | 无 | 不需要处理 |
| id 空间差异 | 存在（不同算例间） | 算法内部统一使用 `o{id}`/`t{id}` 命名，自动适配 |

**需要的数据处理是非传统的"结构化转换"而非"清洗"**：

1. **id 归一化**：评估器和核内调度算法已内置处理（自动区分 op/tensor 空间），无需额外处理。

2. **图结构提取**：将原始二部图（op-tensor-op）转换为 op-op 邻接表——步骤 1 已内置桥接转换。

3. **特征工程**（服务于代理模型和初始种群构造）——详见第四节。

**数据处理对后续模型的影响**：
- 无数据质量问题 → 不需要丢弃任何算例或字段
- 算例规模差异大（30倍）→ 代理模型需使用**比率特征**而非绝对量特征，以保证跨规模泛化

## 三、数据规律分析

### 【数据规律分析】

#### 3.1 操作类型分布

基于 case_010（796 ops，中等代表）和 case_001（1,001 ops）的统计：

| 操作类型 | Pipe | case_010 数量 | 占比 | 特点 |
|----------|------|:------:|:----:|------|
| COPY_IN | PIPE_MTE2 | 93 | ~12% | DDR→片上搬运，固定出现在子图边界 |
| COPY_OUT | PIPE_MTE3 | 36 | ~5% | 片上→DDR搬运 |
| MATMUL | PIPE_M | 131 | ~16% | 矩阵乘法，耗时长 |
| RELU | PIPE_V | 177 | ~22% | 最常见向量操作 |
| REDUCE | PIPE_V | 110 | ~14% | 归约操作 |
| ADD/MUL/SUB | PIPE_V | 162 | ~20% | 逐元素运算 |
| SIGMOID/EXP/NEG/DIV | PIPE_V | 87 | ~11% | 激活函数类 |

**关键规律**：
- **PIPE_M（Cube）操作约占 16%**，高度集中在 MATMUL（矩阵乘法），每个 MATMUL cycles 较长
- **PIPE_V（Vector）操作约占 67%**，种类繁多但单次耗时短
- 图中 COPY_IN/COPY_OUT 约为总 op 的 13~17%

#### 3.2 张量存储压力分析

| 算例 | ops | L1 tensor 总量 | UB tensor 总量 | L1 容量倍数 | UB 容量倍数 |
|------|:---:|:--------:|:--------:|:----------:|:----------:|
| case_001 | 1,001 | 1.64 MB | 1.64 MB | 3.1x | 12.5x |
| case_025 | 23,997 | 24.6 MB | 28.7 MB | **47x** | **219x** |
| case_050 | 4,781 | 0.76 MB | 2.87 MB | 1.4x | 21.9x |
| case_085 | 19,993 | 9.34 MB | 15.97 MB | 17.8x | 122x |
| case_100 | 1,654 | 0.64 MB | 3.70 MB | 1.2x | 28.2x |

**关键规律**：
- 所有算例中，L1 总 tensor 量都超过 L1 容量（3~47 倍），UB 总 tensor 量远超 UB 容量（12~219 倍）
- **这意味着在任何非平凡切图方案下，核内调度必然触发缓存换入换出**
- 问题 1（每子图独立 Task，缓存清空）中每个子图单独运行，压力较小
- 问题 2（每核合并 Task）中合并后的压力取决于子图聚合程度——这是建模的核心挑战

#### 3.3 图结构与拓扑特征

- 所有计算图均为 **DAG**（有向无环图），由评估器的合法性校验保证
- ops、tensors、edges 数量比例稳定在 1 : 1.1 : 2.7 附近
- COPY_IN/COPY_OUT 在原图中已经存在（DDR↔片上的数据通路），切图后会新增边界 COPY
- 图的拓扑结构决定了：**每个 op 的深度位置 ≈ 神经网络的层位置**，同层 ops 可并行
- 张量生命周期紧凑：多数 L1/UB tensor 在 2~5 个相邻 op 之间传递后即被释放

#### 3.4 ops 执行周期分布

| 算例 | 最大 cycles | 平均 cycles |
|------|:----------:|:----------:|
| case_001 | 1,164 | 263 |
| case_025 | 588 | 247 |
| case_050 | 524 | **39** |
| case_085 | 4,120 | 215 |

**关键规律**：
- 平均 cycles 在 39~263 之间波动较大，反映不同神经网络架构的计算密度差异
- case_050 平均仅 39 cycles/op → 大量轻量级向量操作 → 存储压力可能成为更主要的瓶颈
- case_085 最大 cycles 达 4,120 → 存在耗时很长的矩阵运算

---

### 【关键发现】

1. **算例异质性极高**：ops 数从 796 到 23,997（相差 30 倍），存储压力从 1.2x 到 47x 容量，cycles 特征各异。**不能用单一参数配置适应所有算例**——算法需自适应。

2. **存储压力是问题 2/3 的核心瓶颈**：所有算例的总 tensor 量远大于片上容量。切图粒度直接影响溢出频率，溢出又主导了额外搬运量和 Makespan。"切多大"是全局决策，"在哪切"需要局部优化。

3. **图结构具有天然的层状特点**：同一拓扑深度上的 ops 之间没有数据依赖，天然可并行。这一特性可指导切图策略——沿深度方向切分较安全，同层内保持完整有利于核内并行。

4. **PIPE_M 操作（MATMUL）是高价值节点**：约占 16% 但消耗大量 cycles。将 MATMUL 均匀分配到各核心有利于负载均衡。

5. **COPY_IN/COPY_OUT 约占 13~17%**：这些是必需的 DDR 搬运。新增的跨子图 COPY 将进一步增加 DDR 带宽压力——减少跨核数据流是优化的关键方向。

6. **指标之间的"跷跷板"关系**：更细的切图 → 更多跨子图 COPY → 更高 DDR 带宽竞争 → 可能反而增加 Makespan。在 Makespan 和搬运量之间存在权衡，需要 GA 适应度函数同时考虑。

## 四、模型相关的数据处理

### 【数据预处理方案】

结合最终建模方案（GA + 代理模型 + 存储峰值估计器），需要以下结构化数据预处理：

#### 4.1 图结构特征提取（代理模型输入）

**目的**：为代理代价回归模型提供特征，使 GA 能快速预估 Makespan 而不必每次仿真。

**提取的特征**（每种特征在每个图/每个切图方案上计算）：

| 特征类别 | 具体特征 | 计算公式/来源 | 意义 |
|----------|---------|--------------|------|
| **规模特征** | n_ops, n_tensors, n_edges | 直接计数 | 反映图的大小 |
| **存储特征** | L1_total_size, UB_total_size | $\sum s_t$ (按pos) | 存储压力原始值 |
| **存储特征** | L1_capacity_ratio | L1_total / 524288 | 溢出压力相对量 |
| **存储特征** | UB_capacity_ratio | UB_total / 131072 | 溢出压力相对量 |
| **计算特征** | total_cycles, max_cycles, avg_cycles | 统计 ops[].cycles | 总计算量 |
| **管道特征** | pipe_M_ratio, pipe_V_ratio | 各pipe op数/总op数 | 流水线负载分布 |
| **图结构特征** | critical_path_length | BFS/DFS 求最长路径 | Makespan 的理论下界 |
| **图结构特征** | max_width (最大并行宽度) | 同一拓扑深度 max op 数 | 并行潜力 |
| **切图特征** | n_subgraphs, avg_subgraph_size | 当前方案统计 | 切分粒度 |
| **切图特征** | n_cross_edges | 跨子图边数 | 通信开销指标 |
| **切图特征** | cross_tensor_total_size | 跨子图 tensor 总大小 | 通信数据量 |

**处理方法**：
- 所有"总量"特征除以对应算例的总 op 数，转为**比率特征**（适应不同规模）
- 确保代理模型在不同规模的算例间可迁移

#### 4.2 存储峰值快速估计器输入

**目的**：为问题 2/3 的溢出惩罚提供不依赖完整仿真的快速估计。

**处理流程**：
1. 对某核心的子图序列，收集所有 op 和 L1/UB tensor
2. 以简化拓扑序（按深度排序即可）模拟 op 执行
3. 维护当前驻留量：op 产生输出时 +size，op 的末次输入被消费后 -size
4. 记录整个模拟中的最大驻留量

**输入数据形式**：子图序列 → ops_in_order + tensor_lifecycle 映射表

#### 4.3 GA 编码所需数据

**目的**：提供切图编码和调度编码的基础信息。

**处理流程**：
1. 从原图中提取所有非 COPY op 的 id 列表（eligible ops）
2. 按拓扑序排序（Step1 的 seq 输出或简化拓扑排序）
3. 构建 op-op 邻接表（去除 COPY 节点的收缩图）
4. 计算每个 op 的深度和关键路径标识

#### 4.4 样本划分

**训练/测试划分**：代理模型需要训练数据。
- 从 100 个算例中随机选取 **10 个算例** 作为验证集
- 其余 90 个作为 GA 搜索的目标算例
- 代理模型在第一轮 GA 运行中在线收集训练数据（初始种群 + 真实评估 → 特征+标签对），后续迭代中使用

### 【模型输入设计】

#### 最终进入 GA 的数据结构

```
每个算例的输入数据包 = {
    # 原始图数据（JSON 解析后）
    "graph_json": { tensors, ops, edges },
    
    # 预计算的图特征（模块1：图结构分析器输出）
    "features": {
        "n_eligible_ops": <int>,       # 非COPY op数量
        "op_topological_order": [...],  # 拓扑排序后的op id列表
        "op_depths": {op_id: depth},   # 每个op的拓扑深度
        "critical_path_ops": [...],     # 关键路径上的op id
        "tensor_lifecycle": {tid: {first, last, pos, size}},
        "op_adjacency": {op_id: [succ_ids]},  # 收缩后的op-op邻接
        "affinity_matrix": 基于共享tensor的op-op亲和度
    },
    
    # 代理模型特征（每次切图后动态更新）
    "current_solution_features": { ... },
    
    # 硬件配置
    "config": { L1_cap, UB_cap, bandwidth, ... }
}
```

## 五、数据与模型匹配分析

### 【数据适用性分析】

| 模型模块 | 数据需求 | 满足情况 | 评价 |
|----------|---------|----------|------|
| 图结构分析器 | 计算图拓扑信息 | **完全满足** | DAG 结构完整，可直接计算 |
| 初始种群构造器 | op 列表 + 拓扑序 + 亲和度 | **完全满足** | 特征可直接从图中提取 |
| GA 优化引擎 | 适应度值（Makespan） | **完全满足** | 评估器提供精确反馈 |
| 代理代价模型 | 训练数据（特征+标签对） | **需在线生成** | 在 GA 迭代中自然积累 |
| 存储峰值估计器 | 张量生命周期 + 子图序列 | **完全满足** | 简化模型不需要完整仿真 |
| Cache 命中率预估 | COPY_IN 序列 + tensor 信息 | **完全满足** | FIFO 简化模型直接从方案推导 |

**不存在数据不足或信息缺失**。

### 【后续建模建议】

#### 需要重点关注的变量

1. **L1/UB 容量压力比**（L1_total_size / L1_capacity）：此值直接决定问题 2/3 的优化空间。如果合并后的子图该比值 ≤ 1.0，几乎没有溢出；如果 ≥ 5.0，溢出将显著主导 Makespan。**GA 适应度函数必须引入该比值作为惩罚项**。

2. **跨子图边的 tensor 总大小**：决定新增 DDR 搬运量。切图时应尽量在"tensor 小的边"上切，避免在"大 tensor"边上切。

3. **各核心的总 cycles**：负载不均衡会直接导致关键路径延长。GA 在调度编码中需通过 makespan 间接学习，或通过启发式的列表调度来保证。

#### 需要开展的计算实验

1. **单核基线运行**（务必首先完成）：
   - 对 100 个算例逐一运行 `singlecore_evaluate.py`
   - 获得单核 Makespan（用于计算加速比的分母）
   
2. **随机方案采样实验**：
   - 对每个算例运行 stub 方案生成器 10~20 次
   - 获得 Makespan 的经验分布范围，用于设定 GA 的合理搜索目标

3. **代理模型验证实验**：
   - 从初始 GA 迭代中收集 ≥ 500 条（特征，Makespan）数据
   - 训练回归模型并验证 $R^2 \ge 0.7$

4. **存储峰值估计器验证**：
   - 选取 10 个不同规模的算例
   - 比较估计峰值与真实 Step2 输出峰值的误差
   - 目标：平均相对误差 ≤ 25%

5. **GA 参数敏感性分析**：
   - 选取 3 个代表算例（小/中/大各一）
   - 测试不同种群大小、交叉率、变异率组合
   - 确定默认参数和针对大算例的特殊参数

#### 数据处理的注意事项

- **不需要标准化或归一化**：GA 使用原始 Makespan 作为适应度，不需要对特征做标准化。代理模型内部若使用线性回归则需要标准化；若使用树模型则不需要。
- **不需要降维**：特征数量可控（约 15 个），不会导致维度灾难。
- **不需要数据变换**：cycles、size 均为正整数，保持原始值即可。代理模型中转为比率特征（除以对应总量）已足够了。

#### 大算例特殊处理

对于 case_025（23,997 ops）等超大算例：
- 初始种群生成时，限制单次评估的超时（如 60 秒）
- 代理模型的预筛选作用在这些算例上更加关键
- GA 代数可适当减少（如 50 代），利用初始种群的高质量解
