# 2 问题分析

## 2.1 整体求解思路

本题的决策链从计算图出发，依次涉及子图划分、Task 构造、子图到计算核的分配以及各核内的执行顺序。方案经过对应场景的官方 Evaluator 后，才得到 Makespan、Added Copy 等正式评价结果。前一环节会改变后一环节所面对的依赖、并行机会和数据搬运，因此切图与调度不能被视为彼此独立的问题。

困难主要体现在四方面：第一，图依赖限制可并行执行的操作和子图顺序；第二，增加切分可能提供更多并行机会，却也可能增加边界通信、重复读取或核内存储压力；第三，三个问题的 Task 组织、跨核通信和 Cache 规则不同，同一方案在不同场景下的执行结果不能直接互换；第四，划分、核分配及核内顺序组合形成较大的搜索空间，而候选方案还需由官方 Evaluator 完整检查和评价，难以穷举。

据此，本文采用 Baseline 与 Multi-seed 构造初始候选，再以 VNS 对候选方案进行局部改进，并在搜索过程中调用官方 Evaluator 闭环评价。算法只负责生成和调整调度方案；P1、P2、P3 的正式执行差异由各自的 Evaluator 体现。具体方案表示和目标见第4章，求解步骤见第5章。

## 2.2 问题一分析

问题一中，每个子图对应一个独立 Task，子图边界上的数据需要经 DDR 传递。因此，划分不仅决定各核可并行处理的工作，也决定边界数据搬运的范围；核间依赖及同核 Task 的先后关系还会产生等待。若只追求各核计算负载均衡，可能忽略边界通信和数据搬运；若只合并强依赖操作以减少通信，又可能压缩可并行的子图数量。问题一因而需要同时考虑 DAG 依赖、子图粒度、核间分配和核内顺序，并以正式场景评价它们的综合执行结果。

## 2.3 问题二分析

问题二相对问题一改变了 Task 的组织边界和通信语义：同一核心上的子图归入同一个 Task，子图间数据可以通过 L1/UB 驻留复用；跨核依赖仍需通过 `COPY_OUT`、`COPY_IN` 及同步延迟传递。这使得把问题一的划分或调度直接沿用到问题二，不能据此推断其在问题二下仍然合适；必须按问题二的执行规则重新评价。方案需要在同核数据复用、跨核搬运与并行执行之间作出权衡，同时满足核内存储容量要求。

## 2.4 问题三分析

问题三在问题二的跨核执行模型上增加共享只读L2 Cache。`COPY_IN` 的数据读取可能由Cache服务，也可能需要从DDR读取；未命中后的更新和淘汰遵循FIFO规则，因此命中情况还受此前访问及Cache状态影响，不能仅由静态图划分判断。Makespan反映该场景下的正式执行时间，Cache命中率可用于观察访问覆盖情况，但不是本文求解器的优化目标。求解器仍按第4章定义的正式目标比较方案，Cache路径和命中统计则由问题三的官方 Evaluator 处理；因此本文不把方法描述为Cache-aware partition。
